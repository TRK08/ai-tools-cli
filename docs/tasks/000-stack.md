## Решения по применению

- Один npm-пакет; registry-клиент — отдельный внутренний модуль без зависимости от UI. Выделение клиента в библиотеку остаётся возможным позже, без монорепозитория и публичного SDK сейчас.
- Для изменения зависимостей использовать `npm install`, сохранять `package-lock.json` в Git. В CI и для воспроизводимой установки использовать `npm ci`; scripts запускать через `npm run <script>`, аргументы передавать после `--`.
- Собирать JavaScript ESM для Node.js, не standalone executable и не CJS/ESM dual package. Для CLI не требуется публикация деклараций публичной библиотеки.
- Runtime-зависимости, которые tsdown оставляет внешними, должны находиться в `dependencies`: Commander, Clack, yaml, tar. Инструменты разработки — в `devDependencies`. Проверка npm-архива должна подтвердить работу без devDependencies.
- `tsx` выполняет исходники, `tsdown` собирает, `tsc --noEmit` проверяет типы. Эти проверки не заменяют друг друга.
- Oxlint отвечает за правила кода; форматирование остаётся у Prettier.
- Настроить Changesets в каркасе, но не включать автоматическую публикацию, повышение версии или push после задач.
- Для разработки и сборки выбирать поддерживаемую чётную ветку Node; базовая проверка CLI — Node 22.20. На момент исследования tsdown поддерживает build-runtime `^22.18.0 || ^24.11.0 || >=26.0.0`, что совместимо с базовым Node 22.20. Требования сборщика не тождественны `engines` опубликованного CLI.
- Конкретные совместимые версии зависимостей зафиксировать в задаче 001 после проверки их `engines`/peerDependencies, без prerelease и без плавающего `latest` в манифесте. Здесь версии пакетов намеренно не объявлены уже проверенными в установке.

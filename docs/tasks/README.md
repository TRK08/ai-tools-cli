## Цикл одной задачи

1. Прочитать `SPEC.md`, согласованный стек и файл задачи. Убедиться, что зависимость получила аппрув.
2. Внести статус `in_progress` в файл задачи и эту таблицу. Одновременно активна только одна задача реализации.
3. Выполнить её работы и критерии готовности. Изменения последующих задач не выполнять заранее.
4. Провести все проверки задачи, проверку диффа и применимые общие проверки. Записать команды и результаты.
5. Заполнить раздел «Результат для ревью», поставить `in_review`, передать результат пользователю и остановиться.
6. Замечания пользователя отрабатывать в этой же задаче со статусом `changes_requested`.
7. После явного аппрува проверенного результата поставить `approved`, записать дату и цитату. Только после этого можно брать следующую задачу.

Согласование стека не запускает задачу 001. Первое поручение на реализацию даёт пользователь. В начатой последовательности аппрув предыдущей задачи разрешает переход дальше, если пользователь не указал иначе.

## Статусы

| Статус            | Значение                                                       |
| ----------------- | -------------------------------------------------------------- |
| planned           | Работа не начата                                               |
| in_progress       | Реализация текущей задачи                                      |
| in_review         | Результат подготовлен и передан пользователю; ожидание аппрува |
| changes_requested | Пользователь запросил доработку текущей задачи                 |
| blocked           | Есть описанное препятствие; следующая задача не начинается     |
| approved          | Пользователь явно одобрил проверенный результат                |

Метаданные внутри файлов задач — источник статуса. Таблица синхронизируется при каждом изменении. Не ставить `approved` самостоятельно по зелёным тестам. У каждой новой ревизии после замечаний должны быть актуальные результаты проверок.

## Общие проверки перед ревью реализации

После настройки инструментов в 001 выполнить:

    npm run type-check
    npm run lint
    npm run format:check
    npm run test:run
    npm run build

Зависимости фиксируются в `package-lock.json`; в CI и для воспроизводимой установки использовать `npm ci`. Аргументы CLI при запуске через script передаются после `--`, например `npm run dev -- add ./demo -a codex`.

Проверки — без автоматической перезаписи файлов. Отдельно выполнить сценарии из текущей задачи и посмотреть итоговый дифф. Для изменения только документации не требовать запусков отсутствующего CLI: проверить содержание, ссылки и согласованность требований.

Записывать фактические команды, дату, среду и результат. Не скрывать пропущенные тесты за формулировкой «всё проверено». Если внешний backend, нужная ОС или агент недоступны, отметить проверку заблокированной; это не считается её прохождением. Переход дальше требует завершения проверки либо явного согласия пользователя с конкретным исключением.

# Архитектура

Один TypeScript/ESM-пакет. Commander разбирает команды, Clack оформляет интерфейс,
бизнес-операции вызываются напрямую. Публичного SDK нет.
Поддерживаемые сценарии и ограничения описаны в [README](../README.md).

| Модуль                                     | Ответственность                                              | Основные точки входа                          |
| ------------------------------------------ | ------------------------------------------------------------ | --------------------------------------------- |
| [CLI](../src/cli/program.ts)               | Аргументы, диалоги, вывод, код завершения                    | `createProgram`, файлы `*-ui.ts`              |
| [Installer](../src/installer/installer.ts) | Add/update/list/remove, общая копия, подключения, транзакции | `Installer`                                   |
| [Sources](../src/sources/types.ts)         | Снимок одного скилла и его метаданные                        | `prepareLocalSource`, `prepareRegistrySource` |
| [Registry](../src/registry/client.ts)      | Каталог, карточки, разрешение версии, проверенная загрузка   | `RegistryClient`                              |
| [State](../src/state/store.ts)             | Схема lock, переносимые пути, атомарная запись и блокировка  | `StateStore`, `hashDirectory`                 |
| [Telemetry](../src/telemetry/client.ts)    | Ограниченная по времени отправка событий                     | `Telemetry.emit`, `flush`                     |

`RuntimeContext` содержит явные `roots.cwd`, `roots.home`, `env`, `http`.
Чтение настоящего окружения остаётся в [точке запуска](../src/cli.ts).
Sources не знают об агентах и lock; Registry не зависит от интерфейса.

## Основной поток

1. CLI выбирает область/агентов и создаёт Installer с callback подтверждения.
2. Installer берёт блокировку области, проверяет состояние и принадлежность путей.
3. Для registry разрешает версию и показывает карточку до загрузки архива;
   для папки/архива сначала готовит снимок и показывает его метаданные.
4. После согласия применяет общую копию и подключения через `FileTransaction`,
   включая отдельную проектную копию Claude из того же снимка, затем атомарно записывает
   lock. Ошибка изменения прежнего назначения до commit откатывает все копии скилла.
5. Очищает workspace; CLI показывает результат и ожидает `Telemetry.flush()`.

Add/update используют одно ядро установки. Find передаёт в него выбранную registry-версию
с политикой latest. `RegistryFindSearch` отдельно управляет debounce, abort и устаревшими
ответами; `find-ui` рисует выбор через raw keypress и оформление Clack.
Remove выбирает/подтверждает список в CLI и вызывает отдельную транзакцию на каждый скилл.

## Контракты

- `PreparedSource`: готовая папка, имя/описание, постоянный источник, версия,
  хеши и `cleanup()`. Прямой потребитель обязан очистить снимок.
- `InstallationRecord`: источник, версия/политика, хеши, агенты и управляемые пути.
- `InstallationChange`: success/unchanged/partial/failed и признаки изменений содержимого,
  подключений и метаданных. Add дополнительно возвращает skipped; update — skipped/pinned.
- `reviewAdd`/`reviewUpdate`: approve/decline/cancel. Без callback внутренний API применяет
  изменения напрямую; интерактивную политику задаёт CLI.

Общие контракты Installer находятся в `installer/types.ts`. `SourceSelection`
фиксирует выбор и разрешённый артефакт, `InstalledSnapshot` — состояние всех физических копий и назначений до preview,
`InstallPlan` — намерение без I/O. Подробности: [Installer](installer.md),
[Sources](sources.md), [State](state.md), [Registry](registry.md), [Telemetry](telemetry.md).

## Добавление команды

Для новой команды зарегистрируйте аргументы в `createProgram`, вынесите диалоги в
отдельный UI-модуль и вызывайте бизнес-операцию с явным RuntimeContext. Переиспользуйте
StateStore, подготовку источников, пути агентов и renderer таблиц; не запускайте вложенный CLI.
Проверяйте доменное поведение на временных корнях и отдельно — разбор команды/код завершения.

Installer разделён на фасад, координатор install, source, inspection, plan, apply
и events. Sources готовят снимки внутри workspace, которым владеет FileTransaction;
заимствованная установленная копия не очищается. Plan не читает файлы, apply не
выбирает источник и не зависит от сети или диалогов. Блокировка остаётся на всю операцию.

Основные функции и методы имеют русские комментарии `/** … */`: назначение,
специальные результаты и, где нужно, I/O, очистка, блокировка, отмена и ошибки.
Поддерживайте эти пояснения при изменении поведения; правила — в [AGENTS.md](../AGENTS.md).

## Добавление источника

1. Реализуйте адаптер в Sources с результатом [PreparedSource](../src/sources/types.ts).
   Он получает явные корни и временную базу, не знает об агентах и не пишет lock.
   Правила подготовки и владения ресурсами — в [Sources](sources.md#добавление-адаптера).
2. Подключите выбор, разрешение метаданных и подготовку в
   [source.ts](../src/installer/source.ts). Для нового вида постоянной идентичности
   обновите SourceIdentity и строгую проверку [схемы](../src/state/schema.ts).
   Изменения источников/политик сначала согласуются в SPEC.
3. Передайте подготовленное содержимое через InstalledSnapshot/InstallPlan существующему
   apply. Исполнитель файлов не должен получать новый HTTP-клиент или выбирать адаптер.
   Версия, показанная в карточке, используется при подготовке; повторное разрешение latest
   после согласия не допускается.

Проверяйте адаптер отдельно на настоящих временных файлах, затем его подключение через
Installer: конфликт источника, отказ/отмена, повтор, partial и ошибки записи/отката.
Сохраните проверки digest/размера для скачиваемого архива и отсутствие временного URL в lock.

## Добавление агента

Добавьте одну запись в [каталог](../src/agents/catalog.ts): id, label, порядок меню/справки,
пути project/global и kind direct/copy/link для каждой области.
AgentId, State-валидация, предвыбор и справка выводятся из каталога.
Direct допустим для пути общей копии. Copy получает отдельный обычный каталог из
проверенного staging; link — глобальный symlink POSIX / junction Windows. Каталог
агентов не выбирает ОС; различия создания ссылок находятся в файловом helper.
Один хеш записи применяется ко всем физическим копиям; отдельного эталона агента нет.
Сохранённые подключения продолжают использовать путь из lock после смены env.

Проверьте обе области, предвыбор/справку, общую и агентские копии/ссылки, чужой объект,
env-переопределение и последующее использование сохранённого пути.
Существование пути не заменяет ручную проверку обнаружения новым агентом.

## Добавление изменяющей операции

Добавьте метод фасада [Installer](../src/installer/installer.ts), который валидирует запрос
и открывает StateTransaction. Общую установку вызывайте через InstallOperation внутри
этого сеанса; новая файловая операция использует FileTransaction и записывает lock
после успешных изменений. Read/write завершённого сеанса использовать нельзя.
StateTransaction удерживает блокировку, но сам не откатывает уже выполненные записи.

Проверки и подготовку завершайте до мутаций; применение повторно проверяет владение
и содержимое. Планировщик остаётся без I/O. Диалоги и код завершения принадлежат CLI,
условия registry-событий — [events.ts](../src/installer/events.ts).
Отдельно проверьте отказ до изменений, полную неудачу, partial, ошибку commit,
откат и очистку после commit. Правила ресурсов — в [Installer](installer.md#транзакция-и-ограничения).

Тестовый helper изолирует cwd/home/env; HTTP запрещён, пока явно не передан транспорт.
Файловые ошибки, HTTP, подтверждения и терминальные потоки подменяются независимо.

[Git roundtrip](../tests/git-roundtrip.test.ts) входит в обычный Vitest и запускает
исходный CLI через общий тестовый helper; предварительный build не нужен.
На текущей ОС временная установка коммитится и клонируется в отдельный runtime
с NFC/NFD и разными core.autocrlf. Проверяются bytes/hash обеих копий, ignore/attributes
и CLI lifecycle после clone. Git config/hooks/автор и домашние каталоги изолированы.
Обмена репозиториями между ОС в CI нет.

Единый Linux npm-архив устанавливается на всех шести комбинациях ОС/Node.
[Короткий smoke](../scripts/check-package.ts) проверяет готовый tgz и настоящие
local/global bin --help/--version; упаковка и обычные функциональные тесты разделены.
Статус нативных и ручных Windows-проверок хранится в [матрице приёмки](windows-validation.md).

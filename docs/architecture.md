# Архитектура

Один TypeScript/ESM-пакет. Commander разбирает команды, Clack оформляет интерфейс,
бизнес-операции вызываются напрямую. Публичного SDK нет.
Поддерживаемые сценарии и ограничения описаны в [README](../README.md).

| Модуль                                     | Ответственность                                              | Основные точки входа                                                  |
| ------------------------------------------ | ------------------------------------------------------------ | --------------------------------------------------------------------- |
| [CLI](../src/cli/program.ts)               | Аргументы и явная регистрация обработчиков                   | `createProgram`                                                       |
| [Сценарии](../src/cli/commands/)           | Параметры, зависимости, последовательность операций          | `addSkill`, `findSkill`, `listSkills`, `updateSkills`, `removeSkills` |
| [Представления](../src/cli/ui/)            | Карточки, меню, таблицы и решения пользователя               | `createAddUi`, `createUpdatesUi`, `createRemoveUi`                    |
| [Терминал](../src/cli/terminal/prompt.ts)  | TTY-ресурсы, кадры, диалоги, таблицы и индикатор             | `runPrompt`, `select`, `confirm`, `multiselect`                       |
| [Агенты](../src/agents/catalog.ts)         | Настройки подключений, проверка ID и разрешение каталогов    | `AGENTS`, `parseAgents`, `agentSkillsDirectory`                       |
| [Installer](../src/installer/installer.ts) | Add/update/list/remove, общая копия, подключения, транзакции | `Installer`                                                           |
| [Sources](../src/sources/types.ts)         | Снимок одного скилла и его метаданные                        | `prepareLocalSource`, `prepareRegistrySource`                         |
| [Registry](../src/registry/client.ts)      | Каталог, карточки, разрешение версии, проверенная загрузка   | `RegistryClient`                                                      |
| [State](../src/state/store.ts)             | Схема lock, переносимые пути, атомарная запись и блокировка  | `StateStore`, `hashDirectory`                                         |
| [Telemetry](../src/telemetry/client.ts)    | Ограниченная по времени отправка событий                     | `Telemetry.emit`, `flush`                                             |

`RuntimeContext` содержит явные `roots.cwd`, `roots.home`, `env`, `http`.
[CliContext](../src/cli/types.ts) объединяет его с версией CLI и независимыми
`stdin/stdout/stderr`. Настоящие зависимости и argv создаются только в
[точке запуска](../src/cli.ts). [executeCli](../src/cli/run.ts) возвращает код
0/1: справка и сообщения команды идут в stdout, диагностика Commander и итоговая
ошибка — в stderr. Сценарии передают терминалу только пару потоков через
`promptStreams`; неявных process-потоков в них нет.
Sources не знают об агентах и lock; Registry не зависит от интерфейса.

## Направления зависимостей

Регистрация в `program` вызывает `commands`. Сценарии связывают Installer,
Registry и Telemetry с представлениями `ui`; представления используют `terminal`.
Общий терминальный код зависит только от своих компонентов, Node и библиотек
оформления. Он не импортирует команды, каталог агентов, Installer или Registry.
UI получает готовые данные и узкие callbacks, не создаёт HTTP-клиенты и не читает lock.

Базовые типы импортируются у владельцев: `AgentId` и `ConnectionKind` — из
[agents/catalog.ts](../src/agents/catalog.ts), `InstallationScope` и `RuntimeContext` —
из [runtime.ts](../src/runtime.ts). State и Telemetry используют эти модули напрямую.
`installer/types.ts` описывает только контракты Installer; транзитных реэкспортов
базовых типов нет. Операции `parseAgents` и `agentSkillsDirectory` принадлежат
[agents/resolve.ts](../src/agents/resolve.ts), их вызывают и CLI, и Installer.
Каталог и resolver используют общий `state/native-path` для синтаксиса путей,
но не зависят от StateStore или состояния установок.

При чтении графа различайте `import type` и runtime-импорты: типы стираются
при сборке. Например, InstallationRecord ссылается на SourceIdentity, а подготовка
источников использует State/hash. Это обмен контрактами; он не требует вызова
Installer из State или Sources. Настройки агентов, терминала и runtime берутся
напрямую у владельца, без промежуточных модулей совместимости.

`src/cli.ts` получает реальные cwd/home/env, fetch, argv и process-потоки.
Сценарии создают Installer/RegistryClient/Telemetry из переданного CliContext;
фасад Installer создаёт StateStore и внутренние этапы из явного RuntimeContext.
Компоненты с I/O сохраняют узкие подменяемые зависимости. Такой порядок позволяет
проверять сценарии на временных корнях без чтения профиля пользователя.

## Основной поток

1. Общий сценарий `commands/add.ts` выбирает область/агентов и создаёт Installer с callback подтверждения.
2. Installer берёт блокировку области, проверяет состояние и принадлежность путей.
3. Для registry Installer разрешает версию; callback `reviewAdd` в сценарии
   загружает описание именно этой версии с сигналом отмены и передаёт готовый
   `AddCardView` представлению. Запрос остаётся внутри `ui.run`; перед карточкой
   и вопросом индикатор останавливается. Архив скачивается после согласия.
   Для папки/архива Installer сначала готовит один снимок и передаёт его метаданные.
4. После согласия применяет общую копию и подключения через `FileTransaction`,
   включая отдельную проектную копию Claude из того же снимка, затем атомарно записывает
   lock. Ошибка изменения прежнего назначения до commit откатывает все копии скилла.
5. Очищает workspace; CLI показывает результат и ожидает `Telemetry.flush()`.

Add/update используют одно ядро установки. Find передаёт в него выбранную registry-версию
с политикой latest, обходя совпадающие локальные пути через `addRegistry`.
`RegistryFindSearch` отдельно управляет debounce, abort и устаревшими ответами;
сценарий find передаёт экрану фабрику модели. Экран отображает её состояние,
передаёт ввод и закрывает модель при завершении; HTTP-клиент создаёт сценарий.
Remove выбирает/подтверждает список в CLI и вызывает отдельную транзакцию на каждый скилл.

## Терминальный интерфейс

Общие компоненты находятся в `cli/terminal`. `session` владеет своими listeners,
raw mode и состоянием потока; `screen` — кадром, его физической высотой после resize
и скрываемым курсором. `runPrompt` объединяет запуск, отмену, завершение и очистку
диалога: EOF/Esc/Ctrl+C возвращают null, ошибки setup/render/потоков отклоняют Promise
после всех шагов освобождения с сохранением первичной причины. Завершённый output
не получает новые кадры или команды курсора.

`select`, `confirm` и `multiselect` используют этот механизм. Confirm предвыбирает
«Нет», отличает отказ от отмены и сохраняет Y/N без дополнительного Enter для
update/remove. Add по-прежнему требует Enter после перемещения выбора Y/N.
Множественный выбор принимает обычные либо закреплённые варианты и необязательный
локальный фильтр; подписи групп и контекст готовит UI конкретной команды.
Общий компонент не знает об агентах, источниках или установках.

Find сохраняет собственную RegistryFindSearch с debounce/abort и защитой от
устаревших ответов, используя общие screen, навигацию, стили и текстовые операции.
Индикатор использует тот же механизм кадра в одной строке, не захватывает ввод
и появляется только для пары TTY после 200 мс. Подготовка add отдельно владеет
своим сеансом до передачи клавиатуры подтверждению: отмена ждёт очистки операции,
а после согласия Installer завершает транзакцию.

Новые меню подключаются к общим компонентам через PromptStreams и данные вариантов.
Не добавляйте в UI собственные обработчики raw mode, очистку ANSI-кадров и resize.

Владельцы освобождают только свои ресурсы:

| Ресурс                    | Владелец и завершение                                                                                                                          |
| ------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Ввод, raw mode, listeners | `terminal/session.ts` восстанавливает исходное состояние. `runPrompt` закрывает сеанс диалога; `createAddUi.run` — сеанс подготовки.           |
| Кадр и курсор             | `terminal/screen.ts` считает физическую высоту при resize и очищает свой кадр. `runPrompt` завершает диалог по его политике.                   |
| Таймеры индикатора        | `createLoading` очищает задержку/анимацию в `stop` и при завершении `run`; UI останавливает индикатор перед выводом и вопросом.                |
| Debounce и запрос поиска  | `RegistryFindSearch` отменяет прежний запрос и игнорирует поздние ответы; экран find вызывает `close` при завершении.                          |
| Workspace и rollback      | `FileTransaction` владеет временной базой Installer, staging и backup. Прямой потребитель PreparedSource вне Installer сам вызывает `cleanup`. |
| Блокировка и lock         | `StateStore.transaction` держит область до завершения callback; Installer завершает применение/откат/очистку до выхода из него.                |

До согласия add UI передаёт AbortSignal подготовке и загрузке карточки выбранной
версии. Esc/Ctrl+C или ошибка потока ждут завершения I/O и очистки; после согласия
Installer заканчивает транзакцию. UI не удаляет workspace самостоятельно.
После операции сценарий ждёт `Telemetry.flush()` в `finally`.

## Контракты

- `PreparedSource`: готовая папка, имя/описание, постоянный источник, версия,
  хеши и `cleanup()`. Прямой потребитель обязан очистить снимок.
- `InstallationRecord`: источник, версия/политика, хеши, агенты и управляемые пути.
- `InstallationChange`: success/unchanged/partial/failed и признаки изменений содержимого,
  подключений и метаданных. Add дополнительно возвращает skipped; update — skipped/pinned.
- `reviewAdd`/`reviewUpdate`: approve/decline/cancel. Без callback внутренний API применяет
  изменения напрямую; интерактивную политику задаёт CLI.

Общие контракты Installer находятся в `installer/types.ts`. `SourceSelection`
фиксирует выбор и разрешённый артефакт, `InstalledSnapshot` — состояние всех физических копий и назначений до preview,
`InstallPlan` — намерение без I/O. Подробности: [Installer](installer.md),
[Sources](sources.md), [State](state.md), [Registry](registry.md), [Telemetry](telemetry.md).

## Добавление команды

Добавьте обычную функцию в `cli/commands/`, принимающую `CliContext` и типизированные
параметры из `cli/types.ts`. В `createProgram` объявите аргументы/флаги и явно
зарегистрируйте обработчик. Для общих флагов передайте `optsWithGlobals()`.
Сценарий проверяет параметры/TTY, создаёт Installer/Telemetry, организует пакет,
оценивает partial/failed и ждёт `flush` в finally. Верхняя обработка ошибки и
код завершения принадлежат `executeCli`.

Представление в `cli/ui/` получает готовые модели, показывает данные и возвращает
выбор; оно не читает state, не изменяет установку и не получает HTTP/runtime.
`AddCardView` содержит подписи источника/области, установленное имя отдельно от
отображаемого, выбранную версию, описание и сгруппированные назначения. Модель
строит `commands/add-card.ts`; её оформление можно менять без Installer/Registry.
Update/remove показывают preview до проверки подтверждения в сценарии, сохраняя
порядок вывода и поведение `--yes`. Общие меню и индикаторы берите из `cli/terminal`.

Переиспользуйте StateStore, подготовку источников и пути агентов; не запускайте
вложенный CLI. Проверяйте сценарий на временных корнях и отдельно — регистрацию,
переданные потоки и UI на готовых данных. Классы команд, DI-контейнер или middleware
для этого не нужны.

В качестве образца новой читающей команды проследите существующий `list`:
[createProgram](../src/cli/program.ts) регистрирует `-a`/`-g` и вызывает
[listSkills](../src/cli/commands/list.ts). Сценарий получает `ScopeOptions`,
проверяет ID через `parseAgents`, вычисляет область через `scopeOf` и вызывает
`Installer.list`. Затем [renderSkillList](../src/cli/ui/list-ui.ts) получает
готовые записи и PromptStreams и вызывает `renderTable`. Для новой команды
добавляются её параметры, функция сценария и явная регистрация по этому образцу;
собственное представление нужно, если отличается форма вывода.

Изменение карточки add/find начинается с [AddCardView](../src/cli/ui/types.ts).
Например, порядок строк «Версия»/«Описание» меняется только в `card` внутри
[add-ui.ts](../src/cli/ui/add-ui.ts); группировка подписей назначений — в
[addCardView](../src/cli/commands/add-card.ts). Если нужны другие уже доступные
данные карточки, сценарий [addSkill](../src/cli/commands/add.ts) передаёт их модели.
UI не делает дополнительный запрос и подтверждает `installationName`, даже если
отображаемое `name` отличается. Проверки модели находятся в `add-card.test.ts`,
оформления/решений — в `add-ui.test.ts`, HTTP и отмены — в `add-cli.test.ts`.

Installer разделён на фасад, координатор install, source, inspection, plan, apply
и events. Sources готовят снимки внутри workspace, которым владеет FileTransaction;
заимствованная установленная копия не очищается. Plan не читает файлы, apply не
выбирает источник и не зависит от сети или диалогов. Блокировка остаётся на всю операцию.

Основные функции и методы имеют русские комментарии `/** … */`: назначение,
специальные результаты и, где нужно, I/O, очистка, блокировка, отмена и ошибки.
Поддерживайте эти пояснения при изменении поведения; правила — в [AGENTS.md](../AGENTS.md).

## Добавление источника

1. Реализуйте адаптер в Sources с результатом [PreparedSource](../src/sources/types.ts).
   Он получает явные корни и временную базу, не знает об агентах и не пишет lock.
   Правила подготовки и владения ресурсами — в [Sources](sources.md#добавление-адаптера).
2. Подключите выбор, разрешение метаданных и подготовку в
   [source.ts](../src/installer/source.ts). Для нового вида постоянной идентичности
   обновите SourceIdentity и строгую проверку [схемы](../src/state/schema.ts).
3. Передайте подготовленное содержимое через InstalledSnapshot/InstallPlan существующему
   apply. Исполнитель файлов не должен получать новый HTTP-клиент или выбирать адаптер.
   Версия, показанная в карточке, используется при подготовке; повторное разрешение latest
   после согласия не допускается.

Проверяйте адаптер отдельно на настоящих временных файлах, затем его подключение через
Installer: конфликт источника, отказ/отмена, повтор, partial и ошибки записи/отката.
Сохраните проверки digest/размера для скачиваемого архива и отсутствие временного URL в lock.

## Добавление агента

Добавьте одну запись в [каталог](../src/agents/catalog.ts): id, label, порядок меню/справки,
пути project/global и kind direct/copy/link для каждой области.
`directory(roots)` вычисляет каталог по умолчанию только по cwd/home. Необязательное
`environment: { name, suffix }` задаёт env-переменную с альтернативной базой и
добавляемые компоненты пути. Общий resolver проверяет значение до нормализации,
разрешает относительный путь от cwd и оставляет default при пустом значении.
Его точка входа — [agentSkillsDirectory](../src/agents/resolve.ts);
`parseAgents` в том же модуле проверяет ID и убирает повторы без изменения порядка.
Подготовка источников исключает default и активные каталоги всех записей каталога;
особые проверки ID агента в Installer для этого не нужны.
AgentId, State-валидация, предвыбор и справка выводятся из каталога.
Direct допустим для пути общей копии. Copy получает отдельный обычный каталог из
проверенного staging; link — глобальный symlink POSIX / junction Windows. Каталог
агентов не выбирает ОС; различия создания ссылок находятся в файловом helper.
Один хеш записи применяется ко всем физическим копиям; отдельного эталона агента нет.
Сохранённые подключения продолжают использовать путь из lock после смены env.

Проверьте обе области, предвыбор/справку, общую и агентские копии/ссылки, чужой объект,
env-переопределение и последующее использование сохранённого пути.
Существование пути не заменяет ручную проверку обнаружения новым агентом.

## Добавление изменяющей операции

Добавьте метод фасада [Installer](../src/installer/installer.ts), который валидирует запрос
и открывает StateTransaction. Общую установку вызывайте через InstallOperation внутри
этого сеанса; новая файловая операция использует FileTransaction и записывает lock
после успешных изменений. Read/write завершённого сеанса использовать нельзя.
StateTransaction удерживает блокировку, но сам не откатывает уже выполненные записи.

Проверки и подготовку завершайте до мутаций; применение повторно проверяет владение
и содержимое. Планировщик остаётся без I/O. Диалоги и код завершения принадлежат CLI,
условия registry-событий — [events.ts](../src/installer/events.ts).
Отдельно проверьте отказ до изменений, полную неудачу, partial, ошибку commit,
откат и очистку после commit. Правила ресурсов — в [Installer](installer.md#транзакция-и-ограничения).

Тестовый helper изолирует cwd/home/env; HTTP запрещён, пока явно не передан транспорт.
Файловые ошибки, HTTP, подтверждения и терминальные потоки подменяются независимо.

[Git roundtrip](../tests/integration/git-roundtrip.test.ts) входит в обычный Vitest и запускает
исходный CLI через общий тестовый helper; предварительный build не нужен.
На текущей ОС временная установка коммитится и клонируется в отдельный runtime
с NFC/NFD и разными core.autocrlf. Проверяются bytes/hash обеих копий, ignore/attributes
и CLI lifecycle после clone. Git config/hooks/автор и домашние каталоги изолированы.
Обмена репозиториями между ОС в CI нет.

Единый Linux npm-архив устанавливается на всех шести комбинациях ОС/Node.
[Короткий smoke](../scripts/check-package.ts) проверяет готовый tgz и настоящие
local/global bin --help/--version; упаковка и обычные функциональные тесты разделены.
Нативные сценарии и границы автоматизации описаны в [проверках Windows](windows-validation.md).

## Организация тестов

Vitest-проект `unit` проверяет компоненты на собственных временных файлах,
подменяемом HTTP и управляемых терминальных потоках. Он не запускает CLI-процессы,
HTTP-серверы или фасад Installer. `integration` проверяет стыки Installer,
источников, состояния, подтверждений и настоящего I/O, включая Git и HTTP timeout.
`e2e` запускает собранный `dist/cli.mjs` отдельными процессами с локальным registry,
настоящими файлами и изолированными cwd/home/env. Внутренние модули CLI не подменяются.
Меню и клавиши проверяются компонентно, e2e использует `-a`/`--yes` без TTY.

Полные матрицы ошибок принадлежат компонентам, принимающим решение. Интеграции
сохраняют проверки согласованности двух копий, commit/rollback, partial, гонок,
отмены и времени жизни блокировки. Назначение тестов и границы наборов —
в [описании тестов](testing.md).

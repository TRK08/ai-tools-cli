# Работа над ai-tools-cli

## Источники требований

- [Очередь задач и порядок работы](docs/tasks/README.md).
- [Зафиксированное поведение MVP](docs/tasks/SPEC.md).
- [Согласованный стек](docs/tasks/000-stack.md).

Перед работой прочитать эти документы и файл текущей задачи. Соседний `../skills` — источник отдельных функций и тестов; `../ai-tools-core/docs/openapi/swagger.yaml` — контракт backend. Не изменять соседние проекты в рамках реализации CLI.

## Порядок выполнения

1. Выполнять одну задачу реализации за раз в порядке 001–008, 010–011; задача 009 исключена из MVP пользователем 2026-10-13.
2. Начинать задачу только после пользовательского аппрува всех её зависимостей. Первый запуск реализации требует отдельного поручения пользователя: создание документации и согласование стека не означают старт разработки.
3. Перед началом отметить текущую задачу `in_progress` и обновить индекс.
4. Реализовать только её объём; выполнить проверки из файла задачи и применимые общие проверки из индекса.
5. Вписать фактические изменения, результаты команд, ручные проверки и ограничения. Незапущенные и заблокированные проверки явно обозначить; не выдавать их за пройденные.
6. После проверки перевести задачу в `in_review`, предоставить пользователю результат и остановиться. Не брать следующую задачу, даже если все тесты проходят.
7. При замечаниях использовать `changes_requested`, доработать ту же задачу и повторить затронутые проверки.
8. Только явный пользовательский аппрув проверенного результата позволяет поставить `approved`. Записать дату и подтверждающую цитату; синхронизировать индекс. После этого разрешён переход к следующей задаче, если пользователь не попросил остановиться.

Аппрув плана, документа или стека не является аппрувом ещё не реализованных задач. Статусы никогда не повышаются до `approved` автоматически, по результатам тестов или по истечении времени. Если проверка не выполнена, отметить причину и оставаться на текущей задаче, пока пользователь явно не разрешит исключение.

## Границы изменений

- Команда установки — `add`; алиас `install` не добавлять. Событие backend `install` сохраняется.
- Использовать согласованный стек, а не прежний `node:util.parseArgs` из раннего плана.
- Менеджер пакетов — npm; зависимости фиксируются в `package-lock.json`, установка в CI — `npm ci`, запуск scripts — `npm run <script>`.
- Корни файловой системы и HTTP-транспорт подменяются в тестах; реальные установки агентов не затрагиваются.
- Код должен соответствовать `SPEC.md`; изменения договорённостей сначала выносить на обсуждение.
- Не выполнять публикацию npm, push или настройку удалённого репозитория как часть этих задач без отдельного поручения.
- Не создавать дополнительные чаты, подзадачи-агенты или параллельные реализации без отдельной просьбы пользователя.

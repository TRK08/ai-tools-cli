# Подготовка локальной папки

Внутренний адаптер задачи 003 создаёт самостоятельный снимок одного скилла. Он
не устанавливает подключения, не пишет lock и не обращается к HTTP. Installer 004
создаёт базу внутри временного рабочего каталога и очищает всю операцию после commit
или отката; прямые вызовы адаптера используют собственный cleanup.

## Внутренний API

```ts
import { prepareDirectory } from './src/sources/directory.ts';

const prepared = await prepareDirectory('./demo', {
  cwd: runtime.roots.cwd,
  temporaryDirectory: temporaryBase,
});

try {
  // Installer использует directory и contentHash одного и того же снимка.
  await usePreparedSource(prepared);
} finally {
  await prepared.cleanup();
}
```

Это пример контракта: `runtime`, `temporaryBase` и `usePreparedSource` предоставляет
вызывающий код. `cwd` и `temporaryDirectory` должны быть абсолютными. Вызывающий
код заранее создаёт отдельную базу временных данных. Адаптер не создаёт саму базу:
она может находиться внутри исходного проекта, и её создание изменило бы источник.
Каждый вызов создаёт в базе собственный `skills-installer-source-*` с папкой `skill`.

`PreparedSource` возвращает:

- `directory`: абсолютный путь к готовому снимку;
- `name`, `description`: проверенные строки из frontmatter скопированного `SKILL.md`;
- `identity`: `{ kind: 'directory', path }`, где path — абсолютный лексически
  нормализованный путь исходника относительно переданного cwd; корневая symlink
  не меняет идентичность на путь цели;
- `version: null`: версия для папки не выводится из дополнительных полей YAML;
- `contentHash`: SHA-256 готовой папки, вычисленный модулем State;
- `cleanup()`: удаляет только принадлежащий вызову временный каталог; повторный
  вызов допустим. База, источник и другие временные каталоги сохраняются.

State превращает абсолютную идентичность в относительную при записи проектного
lock и сохраняет абсолютную для глобальной области. `archiveHash` у папки отсутствует.

## Метаданные и снимок

В корне нужен `SKILL.md`. Frontmatter начинается первым разделителем `---` и
завершается отдельной строкой `---`; поддерживаются LF, CRLF и BOM. Используется
YAML core schema из установленного пакета `yaml`, без пользовательских и
исполняемых тегов. Обычные aliases допускаются с ограничением раскрытия 100;
дубликаты ключей, ошибки YAML и неизвестные теги отклоняются. Настройки парсера
описаны в [документации yaml](https://eemeli.org/yaml/#options).

`name` и `description` должны быть непустыми строками. Для name применяется
общая проверка State: запрещены `.`, `..`, разделители пути, управляющие символы
и длина более 255 UTF-8 байт. Дополнительные поля YAML сохраняются в исходном
файле, но не влияют на контракт адаптера. Многострочное description допустимо.

Адаптер копирует исходные байты каждого файла, включая `SKILL.md`, бинарные
ресурсы и скрипты. Права обычных файлов `mode & 0o777` сохраняются. Текст, ссылки
в Markdown и пути внутри скриптов не переписываются. Пустые папки, скрытые файлы
и обычные ресурсы с именами `tmp`, `backups`, `operation.lock` включаются.

Корневая ссылка, внутренние и внешние файловые ссылки разыменовываются. Цель
копируется под именем ссылки; ссылки в результате отсутствуют. Повторные ссылки
на одну папку разрешены, если не образуют цикл в текущей цепочке обхода.
Изменение внешнего ресурса после подготовки не меняет снимок.

## Исключения и ошибки

Из обхода исключаются конкретные `cwd/.agents/skills`, собственный корневой lock,
файл блокировки, переданная временная база,
рабочие каталоги `.agents/.skills-installer-work-*` и корневые временные lock-файлы.
`excludedPaths` добавляет абсолютные файлы/деревья, `excludedPrefixes` — абсолютные
префиксы служебных имён. Installer передаёт глобальные пути, если они могут попасть
в источник. Исключения работают и через symlink-алиасы. Корень cwd целиком не
исключается: источник `.` остаётся допустимым, собственные установки и work не
попадают в снимок. Источник внутри служебных деревьев отклоняется. Vercel-lock и
одноимённые ресурсы вне точных служебных путей сохраняются.

Все назначения проверяются на принадлежность снимку. Обход использует byte names
файлов; чтение обычного файла идёт через fd с `O_NOFOLLOW | O_NONBLOCK` и проверкой
типа/dev/inode. FIFO, socket и другие специальные объекты отклоняются до копирования.
Прямые циклы ссылок обнаруживает realpath, циклы папок — цепочка dev/inode.

| Ошибка               | Значение                                                               |
| -------------------- | ---------------------------------------------------------------------- |
| `INVALID_SOURCE`     | Неподходящий корень, служебный источник или небезопасное назначение    |
| `INVALID_METADATA`   | Неверный frontmatter, обязательные строки или имя                      |
| `SOURCE_CYCLE`       | Цикл ссылок                                                            |
| `UNSUPPORTED_ENTRY`  | Специальный файловый объект                                            |
| `PREPARATION_FAILED` | Сбой чтения/копирования/хеширования; исходная ошибка сохранена в cause |

При ошибке собственный workspace удаляется до возврата. Если сама очистка
заблокирована файловой системой, ошибка содержит путь оставшегося workspace и
`AggregateError` с обеими причинами; успешная очистка в таком случае не заявляется.
Ошибка явного `cleanup()` также передаётся вызывающему коду.

Адаптер не блокирует сторонние редакторы и не создаёт атомарный снимок изменяемого
дерева. Замена конечного файла ссылкой и изменение размера обнаруживаются;
полная защита от конкурентной подмены промежуточных папок не реализована.

## Воспроизведение проверок

```sh
npm run test:run -- tests/frontmatter.test.ts tests/directory-source.test.ts
```

Тесты используют временные home/cwd и отдельную базу временных данных. Через
`fileSystem` можно подменить узкий набор файловых операций: тесты имитируют ошибки
чтения, записи, chmod, fstat и очистки, не меняя настоящие установки.

Тест имён с невалидными UTF-8 байтами запускается только на Linux: файловая система
macOS отказала в создании такой фикстуры. Остальные сценарии выполняются на macOS;
полная Linux-матрица относится к задаче 011.
